    1. Objective

    Purpose

    This document describes the plan for testing the prototype of G-TRAMS (Gasan Tricycle Records and Application Management System) developed for the Office of the Municipal Vice Mayor in Gasan, Marinduque.

    The primary objectives of this Test Plan are:

  • To define the exact software modules, functional workflows, and business rules that will undergo systematic verification and validation based on the 8 core system modules.
  • To identify the required testing methodologies, tools, and environments to ensure quality prior to deployment.
  • To specify the roles and responsibilities of the Quality Assurance (QA) team and project proponents during testing.
  • To establish an objective basis for User Acceptance Testing (UAT) and Software Quality Evaluation based on the ISO/IEC 25010 quality model.
  • To ensure data integrity, role-based access control, municipal ordinance compliance (e.g., maximum 2 tricycle units per operator, route zoning), and accurate generation of Franchise Claim Stubs.

    • Scope

    The testing scope encompasses all software components of G-TRAMS implemented on the MERN stack (MongoDB Atlas, Express.js, React, Node.js) hosted on Render. The functional scope covers:

  • Module 1: User Authentication and Registration
  • Module 2: Manage System Settings
  • Module 3: Manage Account Profile
  • Module 4: Submit TODA Records
  • Module 5: Apply and Renew Franchise Applications
  • Module 6: Generate and Download Franchise Claim Stub
  • Module 7: Generate System Reports
  • Module 8: Manage Franchise Cancellation and Revocation

    • 2. Feature Functionality

    Description of the Functions of the System

    Module 1: User Authentication and Registration

  • The system shall allow users to log in securely based on their designated roles (Admin, Staff, Operator, TODA President).
  • The system shall allow Tricycle Operators to register a new user account.

    • Module 2: Manage System Settings

  • The system shall allow administrators to configure operational parameters, including active fiscal year, allowed units per operator, and franchise fee amounts.
  • The system shall allow administrators to manage user accounts, including account activation and deactivation.

    • Module 3: Manage Account Profile

  • The system shall allow operators to update their personal contact details and profile information.
  • The system shall allow users to securely update their account passwords.

    • Module 4: Submit TODA Records

  • The system shall allow the TODA President to submit official membership rosters.
  • The system shall allow System Admin/Staff to review, validate, and update submitted TODA records.

    • Module 5: Apply and Renew Franchise Applications

  • The system shall allow Tricycle Operators to submit new or renewal franchise applications along with the required digital documents.
  • The system shall allow System Admin/Staff to evaluate, approve, reject, or return applications for compliance.
  • The system shall allow Tricycle Operators to track the real-time status and history of their applications.

    • Module 6: Generate and Download Franchise Claim Stub

  • The system shall automatically generate an official Franchise Claim Stub once an application is approved and marked as "Ready for Pickup".
  • The system shall allow operators to view, download, or print the claim stub containing the reference number, payable fee, and municipal hall checklist.
  • The system shall restrict access to the claim stub for applications that are pending, rejected, or cancelled.

    • Module 7: Generate System Reports

  • The system shall allow administrators to generate and filter operational reports such as the franchise master list, renewal lists, and expired franchises.
  • The system shall display summaries and allow exporting of reports for administrative decision-making.

    • Module 8: Manage Franchise Cancellation and Revocation

  • The system shall allow administrators to process voluntary cancellations and record operator violations as grounds for franchise revocation.
  • The system shall automatically update the franchise status to "Cancelled" or "Revoked" upon administrative action.
  • The system shall notify affected operators and allow them to view the official reason or violation records through their portal.

    • Business Rules

    FunctionsBusiness Rules
    **1. User Authentication & Registration****[BR1]** The system must restrict portal access according to user roles (Admin, Staff, TODA President, Operator).
    **[BR2]** The system must not accept duplicate operator registration with the same email or mobile number.
    **[BR3]** Password entries must be securely encrypted using bcrypt before database storage.
    **2. Manage System Settings****[BR4]** An individual operator cannot register or own more than two (2) active tricycle units under a single name.
    **[BR5]** Only authorized System Administrators can configure the active fiscal year, unit quotas, and franchise fees.
    **[BR6]** Deactivated user accounts must be prevented from logging in or filing new applications.
    **3. Manage Account Profile****[BR7]** The system must allow operators to edit their contact information and residential address.
    **[BR8]** Password updates require verification of the existing password before changes are committed.
    **4. Submit TODA Records****[BR9]** Only recognized TODA Presidents can submit official association membership rosters.
    **[BR10]** Admin/Staff must validate that an applicant is listed in the official TODA roster before approving a franchise.
    **5. Apply and Renew Franchise****[BR11]** Mandatory requirements (OR/CR, Driver's License, TODA Certificate, Barangay Clearance, Cedula) must be uploaded before application submission.
    **[BR12]** New franchises receive an initial validity of three (3) calendar years; renewals receive one (1) calendar year validity.
    **[BR13]** Renewals must pre-populate existing operator and vehicle details to avoid redundant data entry.
    **[BR14]** Returned applications must provide corrective remarks explaining the lacking requirements.
    **6. Franchise Claim Stub****[BR15]** The Franchise Claim Stub is automatically generated only after the application is approved and set to "Ready for Pickup".
    **[BR16]** The Claim Stub must display the Application Reference Number, required fees, and municipal hall checklist.
    **[BR17]** The download/print feature must be disabled if the application status is Pending, Incomplete, Rejected, or Revoked.
    **7. Generate System Reports****[BR18]** The system must generate operational masterlists, renewal monitoring reports, and expired franchise lists with export capabilities (PDF/CSV).
    **8. Cancellation & Revocation****[BR19]** Admin/Staff can revoke or cancel an active franchise based on codified violations (fare overcharging, out-of-route, unlicensed driving, reckless operation, non-compliance).
    **[BR20]** Franchise status must immediately update to "Revoked" or "Cancelled", notifying the operator with official reasons.

    3. Testing Strategy

    Application Name Impacted

  • Primary System: G-TRAMS (Gasan Tricycle Records and Application Management System).
  • Environments: Web-based portal deployed on Render (HTTPS) with MongoDB Atlas cloud database and Cloudinary storage.

    • Test Approach

    Validation testing will be implemented using Black Box Testing techniques. Testing will focus on verifying all functional requirements, input boundary limits, role-based security, document uploads, and municipal workflow transitions.

    Features to be Tested

    1. Role-based user login and operator registration.

    2. Administrative system settings (2-unit limit enforcement, fiscal year, fee rates).

    3. Account management (user activation and deactivation).

    4. Operator profile updates and secure password change.

    5. TODA President membership roster submission and admin validation.

    6. Online franchise application and fast-track renewal with digital document uploads.

    7. Application evaluation workflow (Pending $\rightarrow$ For Signing $\rightarrow$ Ready for Pickup $\rightarrow$ Active).

    8. Automated generation and download of the official Franchise Claim Stub with reference number and fees.

    9. Restriction of claim stub access for unapproved applications.

    10. Dynamic filtering and export of system reports (Masterlist, Expirations, Renewals).

    11. Processing of voluntary cancellations and revocation of franchises with violation reasons.

    Features Not to be Tested

  • Direct online financial transactions (payment of franchise fees remains handled through in-person municipal treasurer procedures).
  • Physical printer hardware communications.

    7. Regression Testing

    Regression testing is executed whenever code modifications, bug fixes, or enhancements are integrated into G-TRAMS. This ensures that new adjustments—such as updating fee structures, franchise validity rules, or route zoning parameters—do not negatively impact or break existing features such as operator registration, document uploads, or real-time status tracking. Automated regression suites powered by Jest and Supertest are executed alongside manual smoke tests before any deployment to the staging and production environments.

    8. User Acceptance Testing (UAT)

    User Acceptance Testing (UAT) will be performed by the project proponents, municipal staff, and representative tricycle operators to verify and accept the system before final deployment. UAT will be conducted as the final phase of testing after functional, integration, and system testing is completed.

    In UAT, the following conditions must be met before the test is conducted:

  • Business Requirements must be available and fully approved.
  • Application Code should be fully developed and deployed to the staging environment.
  • Unit Testing, Integration Testing, and System Testing should be completed with 100% pass rate.
  • No Showstoppers, High, or Medium defects in System Integration Test Phase.
  • Only Cosmetic errors are acceptable before UAT sign-off.
  • Regression Testing should be completed with no major defects.
  • All reported defects should be fixed and re-tested before UAT.
  • Traceability matrix for all testing should be completed.
  • UAT Environment (Cloud Staging with MongoDB Atlas) must be ready and operational.
  • Sign-off mail or formal communication from the QA Testing Team certifying that the system is ready for UAT execution.

    Software Quality Evaluation

    After the acceptance testing, Software Quality Evaluation will also be conducted. SQE will be performed by IT Professionals, Practitioners, and selected user respondents (Municipal Staff and Tricycle Operators). Its criteria are based on the ISO 25010 Software Quality Model. This software evaluation will assess software criteria such as functionality, usability, reliability, performance efficiency, compatibility, security, maintainability, and portability, which will be rated using the Likert Scale rating basis.     • 10. Risk Management

    Risk during system testing can be present; that is why risk management is important to carry out testing and to design and execute scenarios such that top business risks are unearthed early and mitigated promptly.

    RiskMitigation Plan
    **SCHEDULE:** Testing schedule is tight. If the start of testing is delayed due to design tasks, the test cannot be extended beyond the UAT scheduled start date.• The testing team will control preparation tasks in advance and maintain early communication with involved parties.
    • Buffer days have been added to the schedule for contingencies.
    **RESOURCES:** Not enough testing devices or resources onboarding late.• Academic schedules, holidays, and team member availability have been factored into the schedule; tasks are distributed evenly across team members.
    **DEFECTS:** Defects are found at a late stage of the cycle; defects discovered late are most likely due to unclear specifications and are time-consuming to resolve.• Defect management procedures are in place to ensure prompt communication, reproduction, and immediate hotfixing of issues.
    **SCOPE:** Scope changes or functionality is not yet finalized.• The functional scope is strictly bounded to the 8 official modules approved by the project proponents and municipal stakeholders.
    **Natural Disasters & Network Outages:** Power or internet interruption in the locality.• Project repositories and databases are cloud-hosted (GitHub, Atlas, Cloudinary); offline test suites and mobile data hotspots are maintained.
    **Non-availability of Independent Test Environment:** Cloud hosting downtime impacting testing schedule.• Local MongoDB Memory Server and in-memory mock testing environments are configured so testing continues regardless of cloud availability.
    **Delayed Testing Due to New Issues:** New defects identified during testing becoming showstoppers.• Continuous automated testing is executed; if new defects are discovered, defect management and issue escalation procedures immediately prioritize resolution.
